# Glossary and resources

Purpose: This document defines ClinicQ terms and gives verified official documentation links and free learning resources.

## Glossary

| Term | Definition |
|---|---|
| Access token | A short-lived JWT used to call protected ClinicQ endpoints for 15 minutes. |
| Active appointment | An appointment with status `BOOKED` or `CHECKED_IN`. |
| Active-only uniqueness | A database rule that blocks duplicate active slots but allows cancelled slots to be reused. |
| Admin | Clinic role that manages staff, doctors, schedules, and reports. |
| Alembic | Python migration tool used to change the PostgreSQL schema safely. |
| Appointment | A booked doctor visit with start time, end time, patient, doctor, and status. |
| Appointment audit log | Append-only record of who changed an appointment status, when, and why. |
| Argon2 | Password hashing algorithm suitable for storing patient and staff passwords. |
| Asia/Kolkata | Display time zone used for ClinicQ dates and patient-facing times. |
| bcrypt | Password hashing algorithm allowed as an alternative to Argon2. |
| Booking window | Allowed booking range from a future time to at most 30 days ahead. |
| Branch coverage | Test metric that checks whether conditional paths execute. |
| Bruno | API client used to store and run the local demo collection. |
| Celery | Python worker system used for Should-scope reminder e-mails. |
| Checked in | Appointment state that means the patient has arrived at the clinic. |
| Concurrency | Multiple requests running at the same time, such as two bookings for one slot. |
| Consultation fee | INR amount charged for a completed doctor appointment. |
| DPDP Act 2023 | Indian privacy law that motivates minimum personal data and clear purpose. |
| Doctor performance report | Admin report with appointments, completed count, no-shows, revenue, and revenue rank. |
| EXPLAIN ANALYZE | PostgreSQL command that shows the actual plan and time for a query. |
| FastAPI | Python web framework used to build ClinicQ REST endpoints. |
| Idempotency key | Stable key for one reminder outbox row per appointment. It lets retries skip rows already marked sent. |
| JWT | JSON Web Token used as the ClinicQ access token format. |
| Leave | Doctor unavailable period that removes slots from availability. |
| Liveness | Health check that says the API process is running. |
| Lockout | Temporary block after 5 failed login attempts in 15 minutes. |
| Mailpit | Optional local e-mail capture tool; inspect its API or built-in console without implementing or styling it. |
| No-show | Appointment state set at least 15 minutes after start when the patient did not arrive. |
| OpenAPI | Machine-readable API description generated by FastAPI. |
| Partial unique index | PostgreSQL unique index that applies only to rows matching a condition. |
| Problem Details | RFC 9457 error format with `type`, `title`, `status`, `detail`, and `instance`. |
| Readiness | Health check that confirms the API can reach PostgreSQL. |
| Refresh token | Long-lived token valid for 7 days and rotated on use. |
| Refresh token family | Group of rotated refresh tokens revoked together when reuse is detected. |
| Revocation | Marking a token unusable before its normal expiry. |
| Role-based access control | Permission model based on Patient, Doctor, Receptionist, and Admin roles. |
| Schedule | Weekly doctor working sessions that generate possible slots. |
| Seed data | Fictional doctors, patients, and schedules loaded for demos and tests. |
| SERIALIZABLE isolation | PostgreSQL isolation level that can abort unsafe concurrent transactions for retry. |
| Slot | A possible appointment start time, 15 minutes long in Must scope. |
| UTC | Time standard used for persisted timestamps. |
| Window function | SQL feature used to rank doctors by revenue without removing detail rows. |
| Recorded fixture | Fictional input committed in the implementation repository and hashed for offline runtime tests. |
| Named volume | Persistent local Docker data retained by normal stop/start. |
| Local lifecycle | Canonical start/stop plus explicitly confirmed project-scoped reset in document 06. |
| Host test driver | Python process outside the app containers that can test shutdown/restart without terminating itself. |

## Suggested reading order

1. Read the README and `01-project-overview.md`.
2. Read users, functional requirements, and business rules.
3. Read data model before writing migrations.
4. Read API specification before coding handlers.
5. Read testing strategy before implementing each feature.
6. Read [06 Tech stack and setup](06-tech-stack-and-setup.md) before installing tools; it defines exact local entry points, ports, seed/fixtures, and resource budgets.
7. Read DevOps rules before opening the first PR.
8. Read interview preparation every Friday after demo.
9. Follow document 09's TC-LOCAL-001 through TC-LOCAL-006 before claiming offline or persistence acceptance. No frontend or public deployment study/build task is required.
